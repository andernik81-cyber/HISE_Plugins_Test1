# HISE_WORKFLOW_NOTES.md

## Проверенный workflow для HISE 4.1.0

Эти заметки сохранены как рабочая инструкция для следующих сессий. Не возвращаться к прежним предположениям, если они противоречат этому файлу.

### 1. Эталонный проект

`TestGainPan2` был создан непосредственно в HISE 4.1.0 и успешно показал интерфейс. Его структура является эталоном для новых проектов.

Типовая структура:

```text
TestGainPan2/
├── Scripts/
│   └── ScriptProcessors/
│       └── TestGainPan2/
│           └── Interface.js
└── XmlPresetBackups/
    ├── TestGainPan2.xml
    └── TestGainPan2UIData/
        └── TestGainPan2Desktop.xml
```

### 2. Главное правило

Не пытаться создавать HISE-проект только редактированием отдельных XML/JS файлов на GitHub.

Сначала нужно иметь реальный проект, созданный/сохранённый HISE. В XML должен существовать настоящий:

```xml
<Processor Type="ScriptProcessor" ID="Interface">
```

Именно этот ScriptProcessor является источником интерфейса.

### 3. Interface.js

Рабочий интерфейс использует:

```javascript
Content.makeFrontInterface(600, 600);
```

Размер 600×600 является проверенным стартовым размером для этого проекта. Не задавать произвольные размеры без необходимости.

### 4. UIData

HISE автоматически создаёт UIData рядом с XML:

```text
XmlPresetBackups/<ProjectName>UIData/<ProjectName>Desktop.xml
```

Этот файл нельзя считать лишним или ошибочным. Он содержит сохранённое состояние/геометрию интерфейса.

### 5. Script Processor и MIDI Processor

В нашем рабочем проекте `Interface` находится как `ScriptProcessor` внутри Master/MIDI processor chain. Не искать отдельный пункт «MIDI Processor» как обязательный шаг, если структура уже создана HISE.

### 6. Параметры

Для управляемых элементов использовать стабильные ID. Не переименовывать существующие parameter IDs после начала работы с проектом без явной необходимости.

Связь UI с DSP проверять по реальным `processorId` и `parameterId`, а не придумывать имена.

### 7. TestGainPan

Текущий рабочий плагин:

- Volume
- Pan
- Stereo meter
- квадратный интерфейс

Сначала проверять, что интерфейс реально загружается в HISE. Только после этого добавлять DSP и визуальную полировку.

### 8. Что было ошибкой в предыдущих попытках

- Нельзя было просто положить `Interface.js` в репозиторий и ожидать, что HISE автоматически подключит его к любому XML.
- Нельзя было вручную придумывать структуру XML вместо копирования проверенной структуры HISE.
- Нельзя путать DSP `Volume/Pan` с GUI ScriptProcessor `Interface`.
- Нельзя удалять `*Desktop.xml`: это нормальная часть UIData.
- Нельзя создавать несколько вариантов `GainPan1`, `TestGainPan` и `interface.js` с разным регистром/именами — это создаёт путаницу.
- Если проект ломается, сначала использовать рабочий проект, созданный HISE, как шаблон.

### 9. GitHub workflow

После изменений, сделанных через GitHub:

1. GitHub Desktop → Fetch origin.
2. Если появились удалённые изменения → Pull origin.
3. В HISE открывать актуальный XML проекта из `XmlPresetBackups`.
4. Не создавать новый проект поверх существующего без необходимости.

### 10. Перед следующей крупной задачей

Сначала проверить структуру текущего проекта в GitHub и сравнить её с реально работающим HISE-проектом. Не делать массовых изменений вслепую.
