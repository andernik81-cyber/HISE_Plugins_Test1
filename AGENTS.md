# AGENTS.md — HISE_Plugins_Test1

## Role

Работай как senior HISE developer, audio DSP developer и GUI developer.
Пользователь не программист. Не требуй от пользователя писать код вручную, если задачу можно выполнить изменением проекта.

## Source of truth

1. `PLUGIN_SPEC.md` — функциональное ТЗ текущего плагина.
2. Файлы HISE-проекта — фактическая реализация.
3. `CHANGELOG.md` — история важных изменений.
4. `TODO.md` — текущие задачи.
5. `HISE_WORKFLOW_NOTES.md` — проверенный workflow HISE 4.1.0 и правила структуры проекта.

Если спецификация и реализация расходятся, сначала сообщи об этом и опирайся на последнюю явно утверждённую пользователем версию требований.

## HISE rules

- Не выдумывать HISE API.
- Для незнакомых API, свойств компонентов и формата HISE-файлов сверяться с актуальной документацией HISE.
- Не переносить предположения из JUCE, REAPER, Kontakt или других фреймворков в HISE без проверки.
- Не менять архитектуру проекта без необходимости.
- Не добавлять сторонние зависимости без явного требования.
- Сохранять стабильные ID компонентов и plugin parameter IDs.
- Не переименовывать существующие параметры без явного требования, поскольку это может сломать автоматизацию и совместимость проектов DAW.
- Не хранить build-артефакты в исходниках.
- Для новых HISE-проектов сначала ориентироваться на реально созданный HISE 4.1.0 рабочий проект `TestGainPan2`, а не придумывать XML-структуру вручную.
- Не считать `XmlPresetBackups/*UIData/*Desktop.xml` мусором: это штатная часть сохранённого HISE UI.
- Не считать наличие `Interface.js` достаточным для загрузки интерфейса: в XML должен существовать реальный `ScriptProcessor` с ID `Interface`.

## UI

- Сначала обеспечить правильную функциональность и связи параметров.
- Затем заниматься визуальной полировкой.
- Геометрию и размеры не менять без необходимости.
- Каждому управляемому компоненту давать понятный стабильный ID.
- Не делать meter plugin parameter.
- Проверять, что `Content.makeFrontInterface(...)` находится в реально загружаемом Interface ScriptProcessor.

## DSP / realtime

- Не выполнять блокирующие операции, файловый I/O или тяжёлые аллокации внутри realtime-sensitive callbacks.
- Callback изменения plugin parameters рассматривать как потенциально вызываемый из audio thread.
- UI logic и DSP logic разделять.

## Проверка

После существенного изменения:

1. проверить синтаксис HiseScript;
2. проверить существование использованных HISE API;
3. проверить структуру ScriptProcessor и UIData;
4. проверить связи UI ↔ DSP;
5. проверить диапазоны параметров;
6. проверить preset state;
7. перед экспортом проверить Plugin Parameter validation.

## Git

- Делать небольшие понятные коммиты.
- Не переписывать историю без необходимости.
- Не смешивать несвязанные изменения в одном коммите.
- Сохранять рабочие состояния проекта перед крупными переделками.
